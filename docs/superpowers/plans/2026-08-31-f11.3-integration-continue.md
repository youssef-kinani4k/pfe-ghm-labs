# F11.3 — Intégration continue : plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Doter LeadFlow d'une CI GitHub Actions qui exécute les tests backend et frontend sur chaque push, et éprouve la pile de production entière par le script de fumée sur `main`, les pull requests et les branches `feature/**` et `fix/**`.

**Architecture:** Un seul fichier `.github/workflows/ci.yml`, quatre jobs. `backend`, `frontend` et `qualite` sont indépendants et parallèles. `fumee` dépend des deux premiers (pour ne pas payer dix minutes quand un test est déjà rouge) et porte une condition sur la référence. La CI fabrique ses propres secrets à chaque exécution : aucun secret GitHub n'est configuré.

**Tech Stack:** GitHub Actions, `actions/checkout@v4`, `actions/setup-java@v4` (Temurin 21), `actions/setup-node@v4` (Node 22), `actions/upload-artifact@v4`, Docker Compose v2, `openssl`, `htpasswd` (apache2-utils), ESLint via `@angular-eslint/schematics`, Prettier 3.

**Spec:** `docs/superpowers/specs/2026-08-31-f11.3-integration-continue-design.md`

## Global Constraints

- **Java 21** (`<java.version>21</java.version>` dans `backend/pom.xml`), distribution Temurin.
- **Node 22** — la machine de développement est en `v22.21.1`, Angular CLI `^20.3.34`. Aucun champ `engines` n'existe dans `frontend/package.json` ; ne pas en ajouter dans cette feature.
- **Spring Boot 4.1.0**, Maven wrapper `backend/mvnw`.
- **`./mvnw verify` s'exécute SANS `-Perp-it`.** Les tests `@Tag("erp")` restent hors CI.
- **Aucun secret GitHub n'est configuré ni requis.** Toute valeur sensible est tirée par le job et masquée par `::add-mask::` avant tout usage.
- **Les mots de passe de service sont hexadécimaux** (`openssl rand -hex`), jamais base64 : `docker compose` interpole les `${...}` à la lecture de `.env.prod`, et un `$` y serait lu comme un début de nom de variable.
- **Chaque `$` du hash BCrypt est doublé** (`sed 's/[$]/$$/g'`), pour la même raison.
- **`.env.prod` n'est jamais téléversé en artefact** et reste ignoré par git (`.gitignore:5`).
- **Le job `qualite` est non bloquant** (`continue-on-error: true`) dans toute cette feature.
- **Aucune correction automatique de style** n'est appliquée : ni `eslint --fix`, ni `prettier --write` sur le code existant.
- Le port publié en CI est **`WEB_PORT=8088`**, donc la cible du script est `http://localhost:8088`.
- Les services de `docker-compose.prod.yml` s'appellent `postgres`, `rabbitmq`, `backend`, `web`.

## Comment lire le résultat d'une exécution

`gh` n'est pas installé sur cette machine. Deux voies, au choix de celui qui exécute :

- **Navigateur** — ouvrir `https://github.com/youssef-kinani4k/pfe-ghm-labs/actions` et lire l'exécution. C'est la voie par défaut de ce plan.

- [ ] **Step 3: Écrire le workflow**

Créer `.github/workflows/ci.yml` :

```yaml
# Integration continue de LeadFlow.
#
# Quatre jobs. Les trois legers tournent sur chaque push, quelle que soit la branche ;
# l'etage de fumee, qui monte la pile de production entiere, ne part que sur main, sur
# une pull request, ou sur une branche feature/** ou fix/**. Le depot est prive et ses
# minutes sont comptees : cette condition, le « needs » et la concurrence sont ce qui
# garde le cout raisonnable.
name: CI

on:
  push:
  pull_request:
    branches: [main]

# Deux poussees qui se suivent sur la meme branche : la premiere execution est annulee.
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  backend:
    name: Backend — tests et paquet
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven

      # Sans -Perp-it : les tests @Tag("erp") demandent de vrais Dolibarr et Odoo, dont
      # la mise en route est manuelle (docs/erp-integration-setup.md). L'etage
      # contractuel des adaptateurs, lui, tourne bien ici.
      #
      # Testcontainers n'a rien a configurer : le daemon Docker est present sur les
      # runners ubuntu-latest.
      - name: mvnw verify
        working-directory: backend
        run: ./mvnw --batch-mode verify

  frontend:
    name: Frontend — tests et build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
          cache-dependency-path: frontend/package-lock.json

      - name: npm ci
        working-directory: frontend
        run: npm ci

      # Chrome est preinstalle sur le runner ; --browsers=ChromeHeadless et
      # --watch=false font une passe unique.
      - name: Tests
        working-directory: frontend
        run: npm test -- --watch=false --browsers=ChromeHeadless

      # Le build compte autant que les tests : il porte les budgets de taille
      # d'angular.json, qui echouent a 1,5 Mo.
      - name: Build de production
        working-directory: frontend
        run: npm run build
```

- [ ] **Step 2: Ajouter le job `fumee` au workflow**

Dans `.github/workflows/ci.yml`, après le job `qualite`, ajouter :

```yaml
  fumee:
    name: Pile de production — script de fumee
    runs-on: ubuntu-latest
    # needs, et pas un job independant : ce job reconstruit les images depuis les
    # sources, donc il recompile le backend de toute facon. Le faire dependre des tests
    # evite de payer dix minutes pour apprendre ce qu un test unitaire vient de dire.
    # « qualite » n'y figure pas : non bloquant, il ne doit rien conditionner.
    needs: [backend, frontend]
    # Sur main, sur les pull requests, et sur les branches de travail. Les fusions se
    # font localement en --no-ff : sans la condition sur feature/** et fix/**, ce job
    # n'apprendrait la panne qu'APRES la fusion.
    if: >-
      github.event_name == 'pull_request'
      || github.ref == 'refs/heads/main'
      || startsWith(github.ref, 'refs/heads/feature/')
      || startsWith(github.ref, 'refs/heads/fix/')
    steps:
      - uses: actions/checkout@v4

      # htpasswd n'est pas garanti present sur le runner. L'installation coute quelques
      # secondes ; la verifier plutot que la supposer.
      - name: Installer htpasswd
        run: |
          command -v htpasswd >/dev/null && exit 0
          sudo apt-get update -qq
          sudo apt-get install -y -qq apache2-utils

      # Aucun secret GitHub n'est configure : chaque execution tire les siens. Ils sont
      # masques AVANT tout usage, pour qu'aucun n'apparaisse dans le journal.
      #
      # Hexadecimal et non base64 pour les mots de passe de service : docker compose
      # interpole les ${...} a la lecture de .env.prod, et un $ y serait lu comme un
      # debut de nom de variable. Le hash BCrypt, lui, en est plein — d'ou le doublage,
      # exactement comme le documente .env.prod.example.
      - name: Fabriquer .env.prod
        run: |
          set -euo pipefail
          PG=$(openssl rand -hex 24)
          RMQ=$(openssl rand -hex 24)
          MASTER=$(openssl rand -base64 32 | tr -d '\n')
          JWT=$(openssl rand -base64 48 | tr -d '\n')
          SMOKE=$(openssl rand -hex 16)
          for secret in "$PG" "$RMQ" "$MASTER" "$JWT" "$SMOKE"; do
            echo "::add-mask::$secret"
          done
          HASH=$(htpasswd -bnBC 10 "" "$SMOKE" | tr -d ':\n' | sed 's/[$]/$$/g')
          echo "::add-mask::$HASH"
          cat > .env.prod <<FIN
          POSTGRES_PASSWORD=$PG
          DB_URL=jdbc:postgresql://postgres:5432/leadflow
          DB_USER=leadflow
          DB_PASSWORD=$PG
          RABBITMQ_DEFAULT_PASS=$RMQ
          RABBITMQ_HOST=rabbitmq
          RABBITMQ_PORT=5672
          RABBITMQ_USER=leadflow
          RABBITMQ_PASSWORD=$RMQ
          LEADFLOW_MASTER_KEY=$MASTER
          LEADFLOW_JWT_SECRET=$JWT
          LEADFLOW_ADMIN_USER=admin
          LEADFLOW_ADMIN_PASSWORD_HASH=$HASH
          WEB_PORT=8088
          GEMINI_API_KEY=
          FIN
          echo "SMOKE_PASSWORD=$SMOKE" >> "$GITHUB_ENV"

      # --keep : sans lui, le trap du script demonterait la pile avant qu'on puisse
      # lire le moindre journal. Une CI qui rougit sans dire pourquoi ne sert a rien.
      - name: Script de fumee
        run: ./scripts/smoke-prod.sh --keep

      - name: Journaux Docker
        if: failure()
        run: |
          docker compose --env-file .env.prod -f docker-compose.prod.yml logs --no-color \
            > docker-logs.txt 2>&1 || true

      - name: Televerser les journaux
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: journaux-docker
          path: docker-logs.txt
          retention-days: 7

      # .env.prod n'est jamais televerse. Le demontage emporte les volumes.
      - name: Demonter la pile
        if: always()
        run: |
          docker compose --env-file .env.prod -f docker-compose.prod.yml down -v || true
          rm -f .env.prod
```

Causes d'échec les plus probables, dans l'ordre :

1. **`SMOKE_PASSWORD non defini`** — la ligne `>> "$GITHUB_ENV"` n'a pas été écrite, ou le pas de fabrication a échoué avant elle.
