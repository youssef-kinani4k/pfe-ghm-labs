# F11.1 — Le socle de déploiement

Design validé le 29 août 2026. Première des trois sessions de F11.

## Le problème

Le pipeline est complet, observable et administrable, mais **il ne sait pas sortir du poste de
développement**. Il n'y a ni image, ni intégration continue, ni profil de production ; CORS
n'autorise que `http://localhost:4200` ; et le seul moyen de lancer l'application est de tenir
trois commandes dans trois terminaux — `docker compose up` pour les dépendances,
`./mvnw spring-boot:run` pour le backend, `npm start` pour le dashboard.

C'est le dernier chantier avant une mise en service, et le seul de la feuille de route qui
n'ajoute aucun écran.

## Le périmètre de cette session

F11 compte huit chantiers que la feuille de route décrit ensemble. Ils ne tiennent pas en une
session, et le découpage retenu est le suivant :

| Session | Contenu |
| --- | --- |
| **F11.1 — celle-ci** | images, Nginx en reverse-proxy, profil `prod`, compose de production, disparition de CORS, test de fumée |
| F11.2 | rate-limiting du webhook, en-têtes HSTS/CSP/`X-Content-Type-Options`/`Referrer-Policy`, restriction SSRF, contournement de `lieResponsable` |
| F11.3 | CI GitHub Actions, et la décision ESLint |

Chaque session est démontrable seule. C'est la raison du découpage : une session qui livrerait
un demi-Dockerfile ne prouverait rien.

**La cible est une pile locale reproductible**, pas un serveur distant. `docker compose` monte
tout sur n'importe quelle machine, en HTTP, sans nom de domaine. TLS est donc hors périmètre,
et HSTS — qui n'a aucun objet sans HTTPS — attend F11.2, où il sera écrit conditionné à
`X-Forwarded-Proto: https`.

## L'architecture retenue

Une **image `web` unique** : Nginx sert l'Angular compilé et relaie `/api` vers le backend.

```
                       :80
                        |
                  [ web ] nginx  ──── / ──────────►  Angular compilé (fichiers)
                        |
                        ├── /api ──────────────────►  backend:8090
                        └── /actuator/health ──────►  backend:8090
                        |
                  [ backend ] JRE 21
                        ├──────────────────────────►  postgres:5432
                        └──────────────────────────►  rabbitmq:5672
```

**CORS disparaît au lieu d'être configuré.** Sous une origine unique il n'y a plus de requête
cross-origin à autoriser : la bonne configuration devient l'absence de configuration. C'est
aussi la topologie que `frontend/proxy.conf.json` simule déjà en développement — la production
devient la version durable de ce qui est utilisé tous les jours, et `environment.apiBaseUrl`,
volontairement vide dans les deux environnements depuis F6, était déjà écrit pour cela.

### Les deux approches écartées

**Un proxy Nginx devant un Nginx statique et le backend** (trois conteneurs) sépare « servir des
fichiers » de « router du trafic ». Ce serait juste avec plusieurs frontends. Il y en a un : on
paierait un conteneur, un saut réseau et un fichier de configuration de plus pour une séparation
dont rien ne profite.

**Spring Boot servant l'Angular depuis `src/main/resources/static`** supprimerait Nginx. Mais le
build Angular devrait entrer dans le jar, ce qui couplerait les deux projets du monorepo au
moment du build ; Tomcat servirait des fichiers statiques, ce qu'il fait mal ; et surtout on
perdrait l'endroit naturel où poseront les en-têtes de sécurité et le rate-limiting de F11.2. On
économiserait aujourd'hui ce qu'on repaierait dans deux sessions.

## Les composants

### `backend/Dockerfile` — multi-stage

Étage de build sur `maven:3.9-eclipse-temurin-21` : le `pom.xml` est copié **seul** et
`go-offline` s'exécute avant que le source n'arrive, de sorte que la couche de dépendances ne se
reconstruise que si le `pom` change. Puis `package -DskipTests`.

Étage de runtime sur `eclipse-temurin:21-jre-alpine` : le jar seul, un utilisateur non-root,
`ENTRYPOINT java -jar`. Ni JDK, ni Maven, ni dépôt `.m2` dans l'image finale.

**Les tests ne tournent pas dans le build de l'image**, et c'est délibéré : `./mvnw test` exige
un daemon Docker pour les Testcontainers Postgres et RabbitMQ, or le build est déjà dans Docker.
Construire l'image et éprouver le code sont deux gestes distincts — c'est la CI de F11.3 qui les
enchaînera.

### `frontend/Dockerfile` — multi-stage

Étage de build sur `node:22-alpine` : `npm ci` — le `package-lock.json` est présent — puis
`npm run build`. La sortie est `dist/frontend/browser` : `angular.json` ne déclare pas
d'`outputPath`, c'est donc le défaut d'Angular 20, et le nom du projet est `frontend`.

Étage de runtime sur `nginx:alpine` : les fichiers dans `/usr/share/nginx/html`, plus le
`nginx.conf` du dépôt.

Effet de bord bienvenu : l'Angular CLI n'écrit plus son identifiant de télémétrie dans le
`angular.json` du dépôt, puisque le build tourne dans un conteneur. Le geste
`git checkout -- frontend/angular.json` reste nécessaire après un `npm test` local.

### `frontend/nginx.conf`

Quatre responsabilités, et pas une de plus :

1. `try_files $uri $uri/ /index.html` — sans quoi le rechargement d'une route profonde comme
   `/leads/42` rendrait `404`, le routage étant côté client.
2. `location /api` en `proxy_pass` vers `backend:8090`, avec `X-Forwarded-Proto`,
   `X-Forwarded-For` et `Host`.
3. `location /api/stream/leads` : le même relais **plus `proxy_buffering off`,
   `proxy_read_timeout 3600s` et `X-Accel-Buffering: no`**. Sans cela Nginx accumule le flux et
   le dashboard temps réel se fige — le battement est toutes les 20 secondes et l'émetteur
   expire à 30 minutes, deux valeurs que `application.yml` porte déjà.
4. Cache long sur les chunks hashés d'Angular, `no-cache` sur `index.html`.

Les en-têtes de sécurité ont leur place dans ce fichier mais **appartiennent à F11.2** : les
poser à l'aveugle maintenant risquerait de casser le flux SSE lu en `fetch` + `ReadableStream`
et les chunks lazy, sans que la session ait le temps de le diagnostiquer.

### `docker-compose.prod.yml`

Un fichier **séparé** du `docker-compose.yml` existant, qui garde son rôle inchangé : les
dépendances du développement, avec ses profils `dolibarr` et `odoo`. Un profil `prod` dans le
même fichier aurait dû surcharger les ports exposés et les mots de passe de développement, ce
que les profils Compose ne savent pas faire.

Quatre services : `postgres`, `rabbitmq`, `backend`, `web`. **Un seul port est publié sur
l'hôte** — le `80` de `web`. Postgres et RabbitMQ ne parlent qu'au réseau interne ; la console
de gestion RabbitMQ (`15672`) disparaît, n'ayant pas d'authentification digne d'être exposée.

L'ordre de démarrage est tenu par `depends_on` avec `condition: service_healthy`. Postgres et
RabbitMQ ont déjà leurs `healthcheck` ; le backend en reçoit un —
`wget -q --spider http://localhost:8090/actuator/health`, busybox le fournit là où l'image JRE
Alpine n'a pas `curl` — pour que `web` ne relaie pas vers un backend encore en train de migrer.

### `application-prod.yml`

Court, parce que `application.yml` est déjà écrit pour la production : tout y passe par des
variables d'environnement et aucun secret n'y a de valeur de repli. Le profil n'ajoute que ce
qui doit différer du développement :

- `logging.level.com.leadflow: INFO` — ni SQL, ni DEBUG.
- `spring.flyway.locations` reste au défaut, `classpath:db/migration` seul : **`db/dev` n'est
  jamais chargé**, la pile démarre sur une base vide, et la première boutique se crée par
  l'écran de F7 — aucun SQL n'est requis pour amorcer une instance.
- `management.endpoints.web.exposure.include: health` : `metrics` et `prometheus` n'ont aucun
  consommateur aujourd'hui et exposent la forme interne de l'application.
- `management.endpoint.health.show-details: never`.

### La propriété CORS, et le garde-fou de démarrage

`SecurityConfig` code aujourd'hui `http://localhost:4200` en dur. Il lira désormais
`leadflow.security.cors.allowed-origins` : la liste vaut `http://localhost:4200` sous le profil
`dev` et **est vide en production**. Vide signifie qu'**aucun `CorsConfigurationSource` n'est
enregistré**, et non qu'une source est enregistrée avec une liste vide — la distinction compte,
parce qu'un CORS configuré à vide reste un mécanisme actif dont il faudrait ensuite se demander
ce qu'il fait des préflights.

Second changement de code : **`LEADFLOW_ADMIN_PASSWORD_HASH` doit faire échouer le démarrage
quand il est vide**, comme `LEADFLOW_MASTER_KEY` depuis F1 et `LEADFLOW_JWT_SECRET` depuis F6.
Aujourd'hui l'application démarre et c'est la connexion qui échoue, sans rien dire de la cause :
un opérateur qui découvre le problème à l'écran de connexion n'a aucun moyen de le
diagnostiquer. Le message nomme la variable. Le repli du profil `dev` reste en place.

Ces deux changements sont du code Java, donc écrits en TDD comme le reste du projet.

### `.env.prod.example` et le `.gitignore`

Le fichier documente les variables et le geste qui produit chacune :
`openssl rand -base64 32` pour la clé maître, `openssl rand -base64 48` pour la clé de
signature, `htpasswd -bnBC 10` pour le hash BCrypt. Les mots de passe Postgres et RabbitMQ y
figurent aussi : ceux du compose de développement sont `leadflow`/`leadflow`, ce qui est sans
conséquence tant que rien n'est exposé, mais les reprendre en production serait une négligence
gratuite.

**Le `.gitignore` ignore `.env` mais pas `.env.prod`** : le motif est exact, pas un préfixe. La
ligne s'ajoute dans le même commit que le fichier d'exemple, jamais après — un fichier de
secrets de production commité par inadvertance serait le pire résultat possible de cette
session.

## Ce qui prouve que ça marche

Un script `scripts/smoke-prod.sh`, en Bash : Git Bash est disponible sur le poste de
développement et les runners de la CI sont des Linux, donc le même script servira en F11.3 sans
réécriture.

Il monte la pile, **attend la santé des quatre services plutôt que de dormir un temps
arbitraire** — RabbitMQ met une trentaine de secondes à devenir sain, et un `sleep` fixe rendrait
le script vert ou rouge selon la charge de la machine — puis déroule un parcours qui traverse
tout le pipeline à travers le proxy :

| # | Geste | Ce qu'il prouve |
| --- | --- | --- |
| 1 | `GET /` puis `GET /leads/<quelconque>` | Nginx sert l'Angular et `try_files` fonctionne |
| 2 | `GET /api/leads` sans jeton → `401` | Le relais atteint le backend, la sécurité est en place |
| 3 | `POST /api/auth/login` → jeton | Le compte opérateur vient du `.env`, non d'un repli de développement |
| 4 | `POST /api/admin/clients` → `publicKey` + `hmacSecret` | Une base vide s'amorce par l'API, jamais en SQL |
| 5 | Signature HMAC en `openssl`, `POST /api/webhooks/leads/{clé}` → `202` | La capture accepte une soumission réelle en production |
| 6 | Rejeu de la même signature → même `eventId` | L'idempotence tient, index unique compris |
| 7 | Attente puis `GET /api/leads` → le lead est présent | La chaîne complète : capture, RabbitMQ, qualification, Postgres, API, à travers quatre conteneurs |
| 8 | `GET /api/stream/leads` : premier battement en moins de 30 s | **`proxy_buffering off` est bien posé** — le piège nommé par la feuille de route, et le seul point que rien d'autre ne peut prouver |

Le script rend un code de sortie non nul à la première étape échouée, en nommant laquelle, et
démonte la pile sauf si on lui passe `--keep`.

**Deux choses qu'il n'asserte pas, volontairement.** Le lead n'ira pas jusqu'à `SYNCED`.
`ClientAdminService.cree` exige un premier commercial et une configuration ERP complète — pour
Dolibarr, `baseUrl` et `apiKey` — donc la boutique du test en a, mais son `baseUrl` pointe vers
une adresse injoignable : le lead atteindra `ROUTED`, puis la synchronisation échouera, trois
tentatives plus tard une ligne apparaîtra dans le journal des morts. C'est le comportement correct, et le prouver demanderait
de monter un Dolibarr dans la pile de production, ce qui n'y a rien à faire. Et l'analyse
d'intention retombera sur `RULES` faute de clé Gemini, ce qui est exactement le repli documenté.

## Les risques, et leur parade

**Le premier build sera long** : Maven télécharge tout, `npm ci` aussi. C'est le prix d'une
fois ; le découpage en couches fait que les reconstructions ne le repaient pas. À ne pas
confondre avec un build en échec.

**Docker Desktop doit tourner** sur le poste. Sans lui rien de cette session n'est vérifiable —
ce serait un blocage d'environnement, pas de code, comme l'est déjà l'échec
`Could not find a valid Docker environment` de `./mvnw test`.

**Le `nginx.conf` est le fichier le plus facile à casser silencieusement** : une erreur de
`location` ne se voit pas au démarrage, seulement à l'usage. Les étapes 1, 2 et 8 du test de
fumée existent précisément pour cela.

## Une correction au passage

Le document de fin de session de F8 affirme que « la notification est le sujet de F11 ». C'est
faux : la feuille de route F8→F14 assume explicitement qu'**aucune notification n'est envoyée au
commercial**, et aucune des sept features ne la couvre. La ligne est corrigée dans le document
d'origine en même temps que cette spec est écrite.
